Data Shell is a contract-driven write gate for the edge of your systems. It validates partner and vendor feeds before they land, and regulatory submissions before they are filed. Rejected records are never published — and every delivery ships with a certificate you can verify.

For data platform and payment engineering teams that receive external feeds they cannot fully trust — where one defective row reaching settlement, a filing, or a partner costs real money and real investigation time.

The recurring failure

A feed publishes defective rows. Afterwards, nobody can prove what happened.

It is the same incident shape, every quarter: a vendor or partner feed lands, the pipeline copies it through, and somewhere downstream a settlement, a filing, or a partner reconciliation turns out wrong. The investigation is archaeology — which rows were bad, when they were received, who delivered them, and whether the published file matches what anyone claims was delivered.

What exists

Detect after delivery

Validation libraries (Great Expectations, pandera) produce a report about rows that have already been written. The write is not stopped.

What exists

Alert an operator

Dashboards and monitors flag anomalies after the batch crossed the boundary. Someone still has to decide, and the batch already landed.

What exists

Reconcile in finance

Totals are compared after the fact. Per-row provenance — which row, which rule, which file version — is reconstructed by hand.

Data Shell

Refuse the write, seal the decision

The boundary refuses to publish rows it cannot account for, quarantines the rest with the exact rule that held them, and signs a certificate binding feed, decision, and delivered bytes.

The distinction is not “better validation.” It is that the publication decision moves to the one place where it can still be enforced — and that the decision leaves evidence an operator, an auditor, or a counterparty can verify without trusting anyone’s recollection.

The boundary

A write gate, not a report.

Most data-quality tooling observes after the fact: a dashboard lights up, a Slack alert fires, and someone backfills a warehouse that has already served bad rows downstream. Data Shell moves the check to the boundary — the last place where you still control whether a record is written.

Rejected records are never published

Every record is cast and validated before anything is written. A record that fails is quarantined to a tenant-scoped location and indexed with the exact rule that held it — “drop the row” is a decision you declare, not an accident you discover.

Every run is sealed

The active target, an immutable lineage artifact, and a certificate commit together. The certificate binds the contract, source bytes, delivered bytes, and every quarantine file by content hash and path, then signs the result with HMAC-SHA256 — or Ed25519, so third parties can verify from a public key alone.

Built for the feeds that can hurt you.

Teams whose inputs arrive from outside their trust boundary — partner feeds, vendor payouts, claims and filings — where a bad row is expensive and “prove it” is a compliance requirement, not a preference.

Vendor settlements & payouts

The engine ships a settlement ledger, not just checks: exact minor-unit calculation bound to one immutable contract version, dispute and billing-instruction flows, and acceptance/pricing semantics your counterparties can be held to.

Partner & affiliate data onboarding

One versioned contract per partner — reviewed, diffed, rolled back like code. Every rejected record lands in tenant-scoped quarantine with the exact rule that held it, and the gateway rate-limits and refuses oversized payloads before they touch the pipeline.

Claims & regulatory submissions

Batch gates — row-count floors, composite uniqueness, out-of-core SQL assertions — plus zero-deficit footing, and a signed certificate an auditor can verify offline, from content hashes alone.

Boundary honesty cuts both ways: if your inputs are first-party and already inside your trust perimeter, a validation library is the better-shaped tool. This page is written for the controlled-perimeter case.

How it works

Four stages. Any stage can stop the run.

Records pass through four sequential checks. If one fails, the run terminates before a single row is published — and the terminal outcome is recorded.

  1. 01 / STRUCTURAL

    Strict cast at the door

    Each record is cast against the declared schema per-row. A value that cannot be realized is refused and indexed — never silently coerced into something it is not.

  2. 02 / SEMANTIC

    Rules inside

    Row rules run vectorized (Polars); batch rules run out-of-core (DuckDB). The fast path only engages on chunks that already match the schema, so strictness is never traded for speed.

  3. 03 / RECONCILIATION

    The arithmetic must foot

    A single unaccounted-for row refuses the entire run instead of publishing a partial dataset.

  4. 04 / PUBLISH

    Atomic & crash-recoverable

    Target, lineage, and certificate commit through a write-ahead journal and are recovered at startup. Quarantine evidence survives the rejection.

What the contract buys you

  • Reproducible A versioned artifact your team reviews, diffs, and rolls back — not application logic buried in a service.
  • Portable The same contract runs from the CLI, the HTTP gateway, or an Airflow task. Identical verdict.
  • Auditable Every held row names its rule; every refused row names its structural reason.
  • Extensible Ship your own row/batch check types as plugins — built-ins stay closed and cannot be shadowed.
  • Fail-closed If the feed cannot be accounted for, nothing is delivered.

Evidence your auditors can hold.

What the certificate gives you

  • Arithmetic, not claims The reconciliation block is a zero-deficit equation: rows read = delivered + held + refused, with unaccounted_for as a hard-zero field.
  • Offline verification datashell verify recomputes hashes and the signature locally — you never have to trust the reporter.
  • Third-party verifiable Provision an Ed25519 key and the header becomes third_party_verifiable: true: any holder of the public key can verify without a shared secret.
  • Durable The boundary ledger persists delivered, rejected, and failed runs per tenant — queryable and machine-readable.
  • Complete even when refused Quarantine artifacts are hashed into the same Merkle root; a run that rejects still ships proof of what it rejected.

Where it fits

One boundary call in a workflow you already run.

Data Shell does not replace your orchestrator, storage, or alerting. It sits between an incoming feed and the write you currently perform, and owns exactly one decision: does this batch cross the boundary, and with what evidence?

CSV, JSONL, or Parquet — delivered on your existing schedule or landing path.

Does it replace an existing component?

No. It replaces the moment you copy or load a feed straight through. Orchestration, storage, and alerting keep their jobs.

What happens when the data is invalid?

Refused rows never enter the delivered file; held rows are quarantined with the rule that caught them; the run exits 2 under REJECT_RUN policy with zero rows published.

What happens when Data Shell itself fails?

Fail-closed: nothing is published, the exit code is 1, and your existing alerting sees a failed job — the same shape as any other pipeline failure. Write-ahead journals recover interrupted publications at startup.

Can we keep control of retries and alerts?

Yes. The boundary returns an exit code and a JSON summary; your scheduler owns every subsequent decision.

How do we remove it during evaluation?

Point --source/--target back at the legacy path. The CLI is stateless apart from the durable ledger; nothing about adopting it changes your storage layout.

What does the downstream consumer receive?

The delivered artifact only. The certificate, ledger entry, and quarantine are evidence for operators and auditors — not pipeline inputs.

Trust & deployment maturity

          
What is tested, what is designed, and what is still an assumption.

          
We would rather be precise than flattering. Here is exactly where the system stands, and what an approver should validate before a pilot.

        


        

          
AreaStatus

          
            
Security postureHardened — startup rejects weak/seeded secrets, RBAC on every route, rate limiting, non-root read-only container, artifact paths validated before use. CI enforces a zero-findings bandit policy and an OSV dependency audit on every push.

            
Behavior when Data Shell failsFail-closed: nothing is published, the process exits 1, and write-ahead journals recover interrupted publications at startup. Your scheduler sees a normal failed job and routes it to your existing alerting.

            
Reconciliation invariantsZero-deficit accounting is a hard gate: rows read = delivered + held + refused; one unaccounted row refuses the run instead of publishing a partial dataset. Enforced across 522 tests, including streaming and REJECT_RUN parity.

            
Publication atomicityTarget, lineage artifact, and certificate commit together through the journal; a crash mid-publication leaves no half-written target, and recovery is verified by tests.

            
Resource limits20 GiB per-upload ceiling (override MAX_UPLOAD_SIZE_BYTES); concurrency and rate limits are process-local per worker and per replica — size hosts accordingly before scaling horizontally.

            
Reference topologySingle replica and single worker. The credential registry and rate limiter are process-local by design.

            
Scaling surfacesFive documented, environment-tunable surfaces — ingest backend (auto/memory/stream), batch size, SQL threads, delivery codec, concurrency/disk — in docs/SCALING.md with worked profiles. benchmarks/streaming_profile.py measures the out-of-core path's wall time and peak RSS on your hardware.

CertificationNone claimed. Code-level checks are not a substitute for a deployment-specific threat model and independent review.

            
Horizontal scaleBeyond the reference topology — requires shared credential/rate-limit stores before running multiple replicas.

            
Certificate semanticsProves integrity and authorship; it does not prove sender identity. Pair it with your own trust anchor.
