Contract-driven boundary enforcement

Bad data never lands,
and never leaves.

Data Shell is a write gate at the edge of your systems. It validates partner and vendor feeds before they land, and regulatory submissions before they are filed — refusing, quarantining, and binding every terminal outcome to a cryptographically verifiable certificate.

The problem: leaks and blind spots

Bad records are usually discovered downstream — after they have corrupted a warehouse, broken a report, or triggered a regulatory finding. By then the damage is done and the evidence is gone.

The shift: a write gate, not a report

Data Shell inspects at the boundary — the last place you still control the outcome. Rejected records are never published. The gate is the product; dashboards are a by-product.

The result: proof, not promises

Every run commits atomically and is sealed with a signed certificate. Flip a byte after delivery and verification fails; restore it and verification passes. That is tamper-evidence you can test.

How it works

A four-stage gate where every stage can stop a run

Records flow through four sequential checks. Any stage can refuse the run before anything is published — and each terminal outcome is recorded.

T1 Structural

At the door

Strict, per-row schema casting. Records that cannot be realized are refused and indexed — never silently coerced into a value they are not.

T2 Semantic

Inside

Vectorized row rules (Polars) and batch rules (DuckDB, out-of-core when streaming). The fast path runs only when a chunk already matches the declared schema; otherwise rows are validated one by one.

T3 Reconciliation

The arithmetic has to foot

read = refused + held + delivered. A single unaccounted-for row refuses the run instead of publishing a partial dataset.

T4 Atomic publish

Crash-recoverable

The active target, an immutable lineage artifact, and the signed certificate commit together through a write-ahead journal and are recovered at startup. Quarantine evidence survives rejection.

What a contract declares

Sources and formats, a strict schema, row + batch quality rules, a drop/quarantine behaviour, delivery targets, and a quarantine path. It is a versioned, reviewable artifact — not hidden application logic.

apiVersion: daas/v1 · kind: DataProduct

What happens to a rejected row

It is quarantined to a per-tenant location and recorded in the ledger with the rule that held it (or the structural reason it was refused). Nothing about the rejection is invisible.

quarantine → evidence, not a silent drop

          Capabilities
          
Everything the gate does, end to end

          
One engine, available as a local CLI and as a multi-tenant HTTP gateway.

        

        

          

            

            
Refusal-first write gate

            
Four sequential stages, each able to stop a run before publication. Strict Tier-1 semantics are preserved even on the vectorized fast path.

          

          

            

            
Verifiable certificates

            
Each run emits a certificate bound to the contract, the source bytes, the delivered bytes, and every quarantine artifact — by hash and path — sealed with an HMAC-SHA256 envelope.

          

          

            

            
Durable boundary ledger

            
An append-only, tenant-isolated forensic record of every terminal run — delivered, rejected, or failed — with a quarantine index, usage metering, and rolling drift baselines.

          

          

            

            
Multi-tenant RBAC & isolation

            
Four roles and six capabilities. Delivery roots are partitioned per tenant; cross-tenant delivery attempts and cross-tenant certificate reads are denied with an explicit 403.

          

          

            

            
Bounded memory & disk at scale

            
Out-of-core streaming keeps memory bound to the micro-batch, not the file. The built-in upload ceiling is 20 GiB, and runs preflight free space and refuse to start rather than fail mid-run.

          

          

            

            
Observability

            
Prometheus metrics at /metrics for rows read, delivered, held, footing errors, and run duration. Tenant, contract, and rule IDs are deliberately excluded from labels to avoid cardinality blow-up and data leakage.

          

          

            

            
Orchestration & events

            
A productized CLI (run | validate-contract | verify | ledger | demo), an Apache Airflow provider, and signed run.completed webhooks for PagerDuty, Jira, or a SIEM.

          

          

            

            
Formats & deployment

            
Streams CSV, JSONL/NDJSON, and Parquet. Ships as a non-root, read-only container with Docker Compose, Kubernetes (single replica + PVC), and a Render blueprint.

          

          

            

            
Exit codes as contract

            
0 delivered, 2 rejected by policy, 1 engine failure. The gate's verdict is legible to a shell script, a scheduler, or an operator on call.

          Production posture
          
Hardened for single-replica production. Not independently certified.

          
We would rather be precise than flattering. Here is exactly where the system stands.

        

        

          

            

              
✓ In place in this revision

              
    
                
  • Production startup rejects missing or identical API/HMAC secrets, wildcard CORS, non-HTTPS origins, and malformed limits.
    • 
                
  • Non-root container with a read-only root filesystem; Kubernetes ships a readiness probe, security context, and PVC.
    • 
                
  • Readiness fails if the durable ledger cannot be opened; startup recovers interrupted publishes before serving.
    • 
                
  • Strict per-row validation is never weakened for speed; the fast path only runs on schema-matching chunks.
    • 
                
  • Signed certificates verify the signature before dereferencing artifact paths.
    • 
              

            

          

          

            

              
△ Honest boundaries

              
    
                
  • The reference deployment is single-replica: the credential registry and rate limiter are process-local. Run one replica and one worker.
    • 
                
  • No third-party certification is claimed. Code-level checks are not a substitute for independent review.
    • 
                
  • A dependency lockfile, shared stores for horizontal scale, and deployment-specific load/soak tests are required before a real launch.
    • 
                
  • Certificates prove integrity and authorship, not identity of the sender — pair them with your own trust anchor.
    •
