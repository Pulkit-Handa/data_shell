# Data Shell — Residual Risk Register

**Version:** 1.1
**Date:** 2026-10-21
**Branch:** `production_hardening`

Every risk below is stated with its severity, the concrete consequence, the
evidence gap that remains, the next step, and whether it blocks a general
production release. Nothing here is labelled an "enhancement" to disguise
unfinished P0/P1 work.

Severity: **P0** = catastrophic (data loss, compromise, false evidence);
**P1** = high (broken workflow or unverified boundary); **P2** = medium;
**P3** = low.

---

## Blocking risks (must be closed before general production)

| ID | Sev | Risk | Consequence | Evidence gap | Next step | Blocks general release? |
|---|---|---|---|---|---|---|
| RR-001 | P0 | **No independent security review.** The local agent's own static analysis is not an independent review. | An exploitable authz, path, or isolation defect could ship. | `bandit` and `pip-audit` are clean and the security suites pass, but no qualified third party has attacked the code. | Issue `docs/production/SECURITY_REVIEW_PACKAGE.md` to a qualified independent reviewer; obtain the signed report. | **Yes** |
| RR-002 | P1 | **No live deployment verification.** | Deployment-specific behaviour (volume permissions, health checks, ingress, TLS) is unproven. | Local single-process start-up, readiness, and API paths were executed; the container, ingress, and volume mount were only inspected. | Execute `docs/production/DEPLOYMENT_VERIFICATION.md` end to end against the target environment. | **Yes** |
| RR-003 | P1 | **Production capacity is unqualified.** | A 1 GiB feed could exceed the host's memory or disk budget, failing a partner delivery. | 1 GiB completed locally on a shared dev block volume: narrow 837.2 MiB peak; 100-column wide Parquet 2,127.3 MiB peak (CSV 1,115.3 MiB). This is not production hardware, and concurrent-job contention is unmeasured. | Run the § 7 drill in `docs/production/BENCHMARK_PROCEDURE.md` on the pilot host; set `MAX_UPLOAD_SIZE_BYTES` to the largest size that passes. | **Yes** |
| RR-004 | P1 | **No measured production RPO/RTO.** | A recovery could take far longer than assumed, or lose more data than the backup interval. | The isolated drill restored 20 files in 0.01 s and re-verified every certificate, but on a local directory with a tiny dataset. | Run the target drill in `docs/production/BACKUP_RESTORE_DRILL.md` § 4 and record the values. | **Yes** |
| RR-005 | P1 | **No named operator, data owner, security owner, or release authority.** | An incident has no accountable responder; rollback has no decider. | The runbooks deliberately leave the names blank — an organisational decision this repository cannot make. | Assign the four roles and record them in the release checklist. | **Yes** |
| RR-006 | P1 | **Alert delivery is unverified.** | Disk exhaustion, reconciliation failure, or a failed publication could go unnoticed. | Rule definitions exist in `deploy/prometheus-alerts.yaml` and the metrics exist, but no alert was observed firing. | Trigger each condition in a pilot environment and confirm delivery to the on-call channel. | **Yes** |

## Non-blocking risks (accepted for the controlled pilot)

| ID | Sev | Risk | Consequence | Evidence gap | Next step | Blocks general release? |
|---|---|---|---|---|---|---|
| RR-007 | P1 | **Single-replica only.** The credential registry is local SQLite and the rate limiter is process-local. | Scaling out would give divergent key revocations and independent rate limits. | Documented and enforced by the deployment manifests (`replicas: 1`, `--workers 1`). | Move to a shared credential store and a distributed limiter *before* any scaling. | No (pilot is single-replica); **yes** if multi-replica is ever claimed |
| RR-008 | P1 | **An external consumer that reads the delivery target by path — without resolving the generation pointer — can observe a superseded generation.** | A consumer could act on a superseded delivery set. | Narrowed and made explicit in `docs/production/GENERATION_CONTRACT.md`: the pointer is the commit point, the CLI verifier and the HTTP certificate endpoint both report the committed generation from one shared implementation, and a superseded run's *own* evidence (immutable lineage copy + certificate) remains valid. The residual case is an external consumer that ignores the pointer; the certificate's digest check detects it if the consumer verifies. | Publish the pointer contract in consumer onboarding; require certificate verification for consumers of the active target. | No |
| RR-009 | P2 | **Certificates do not prove data truthfulness or semantic correctness.** | A customer could over-read what a valid certificate means. | Stated explicitly in the certificate semantics and the security review package. | Keep the wording in customer-facing material. | No |
| RR-010 | P2 | **Backup captures the raw inbound `data/` directory.** | Backup volume and retention cost may exceed expectations, or raw data may leave the site. | The drill shows the whole storage root is captured. | Operator decision: prune before backup, or exclude the directory. | No |
| RR-011 | P2 | **Backups are not encrypted by the tooling.** | A stolen backup directory exposes feed content. | The tooling copies plaintext; the manifest carries checksums, not encryption. | Encrypt the backup volume or directory at the infrastructure layer. | No (deployment control) |
| RR-012 | P2 | **Retention pruning runs at startup, not on a schedule.** | Evidence may grow between restarts. | Pruning exists and is idempotent; a non-positive retention keeps everything. | Add a periodic job if retention is set to a bounded value. | No |
| RR-014 | P2 | **The live Stripe path has never been exercised.** | A billing integration failure would be discovered late. | The adapter is draft-invoice-only and dry-run is the default; no live credentials were used. | Keep live billing disabled for the pilot. | No |
| RR-015 | P3 | **The demo UI's per-client rate limit is a fairness control, not a security boundary.** | Abuse is bounded by the identity-independent global ceiling instead. | Documented in the threat model. | Keep the global ceiling enforced. | No |
| RR-016 | P3 | **No SSO/SCIM; credential revocation is manual.** | Credential lifecycle is operator work. | Deliberate scope exclusion for a single-tenant pilot. | Add an identity provider before multi-tenant SaaS use. | No |

## Defects found and closed in this cycle

| ID | Sev | Defect | Fix | Verification |
|---|---|---|---|---|
| RR-F01 | P0 | **The generation pointer was write-only.** No production reader resolved it, and recovery never repaired it — so a crash between artifact rename and pointer swap left the pointer naming the old generation while the files held the new one. | `datashell/core/commit.py`: `_recover_locked` now rewrites the pointer from the durable journal's `run_id` when the journal is in the `committed` state; added `resolve_committed_generation()` and `committed_generation_status()`. | `tests/test_publication_coherence.py` — the pointer-repair test fails without the fix and passes with it; the reader tests prove a superseded certificate is reported as such. |
| RR-F08 | P1 | **The reader contract was asymmetric between surfaces.** The CLI verifier reported whether a certificate was the committed generation, but `GET /api/v1/runs/{run_id}/certificate` did not — an API consumer could not distinguish a current certificate from a superseded one, and the two surfaces could drift. | `datashell/core/commit.py`: added `committed_generation_status()` as the single implementation; `datashell/cli/main.py` and `datashell/server/app.py` both call it. | `tests/test_publication_coherence.py::test_api_certificate_endpoint_reports_the_committed_generation` and `::test_api_and_cli_agree_on_the_committed_generation`; the end-to-end CLI run reports `committed generation: <run_id> (this certificate: yes)`. |
| RR-F09 | P1 | **Two runs sharing an audit path overwrote each other's pending ledger record.** The outbox file name was derived from the audit path alone, so two runs targeting the same audit directory raced on one file — one run's payload could be replaced by the other's before either was written to the ledger. | `datashell/core/ledger.py`: the pending-outbox name now includes the `run_id`; the legacy name is still written and still discovered, so no record is orphaned by the change. | `tests/test_ledger_outbox.py::test_concurrent_runs_do_not_overwrite_each_others_outbox` and `::test_two_pending_runs_replay_independently` (two runs → two outbox records → two usage rows). |
| RR-F10 | P1 | **A failed publication left a pending ledger record describing a delivery that never happened.** The outbox is written *before* publication; on a publication failure the record survived, so every later reconciliation re-reported a non-existent delivery. | `datashell/pipeline/runner.py`: `_publish_with_pending_outbox()` removes the record when publication raises, and the removal is per-run so a concurrent run's record is untouched. | `tests/test_ledger_outbox.py::test_failed_publication_leaves_no_pending_outbox` — the test fails when the cleanup is reverted and passes with it. |
| RR-F02 | P1 | **Replay duplicated quarantine index rows.** `record_quarantine` used a plain `INSERT` and the table had no unique identity, so replaying a pending ledger entry duplicated forensic records. | `datashell/core/ledger.py`: unique index on `(tenant_id, run_id, kind, COALESCE(artifact_path,''))`, with a migration that collapses legacy duplicates first; `record_quarantine` now uses `INSERT OR REPLACE`. | `tests/test_ledger_outbox.py::test_replay_does_not_duplicate_quarantine_records` and `::test_legacy_duplicate_quarantine_rows_are_collapsed`. |
| RR-F03 | P1 | **A run could be marked `COMMITTED` with incomplete accounting.** The run row, quarantine rows, and usage row were three separate writes; a failure between them left a committed run without its usage basis. | `datashell/core/ledger.py`: new `apply_run_outcome()` writes all three in one SQLite transaction; both the live path and the replay path use it. | `tests/test_ledger_outbox.py::test_run_is_not_marked_committed_with_incomplete_accounting`. |
| RR-F04 | P1 | **A failed publication could be replayed as a successful delivery.** The pending outbox is written *before* publication, so an outbox outliving a failed publication described artifacts that were never published. | `datashell/pipeline/runner.py`: replay verifies the run's own artifacts exist before committing it; a record whose artifacts are absent is skipped and left for the operator, with an ERROR log. | `tests/test_ledger_outbox.py::test_replay_refuses_to_commit_a_run_whose_artifacts_were_never_published`. |
| RR-F05 | P2 | **Reconciliation failures were silently swallowed.** Skips were counted but never logged, and the startup gate only logged when something was replayed — unreconciled state was invisible. | `datashell/pipeline/runner.py` + `datashell/server/app.py`: every skip logs at ERROR; startup reports `skipped` and `journal_errors`. | Covered by the tests above plus the startup-recovery ordering test. |
| RR-F06 | P2 | **The volumetric benchmark could not run** — it wrote to a relative `./output` that no longer resolved under a configured storage root, so the harness aborted with `ValueError`. | `benchmarks/volumetric_stress_test.py` now uses the configured output/audit directories. | The harness ran to completion at 10 k – 1 M rows with every assertion passing. |
| RR-F07 | P2 | **The API benchmark measured the wrong thing** — it offered concurrency 8 against a configured limit of 2 and recorded 48/50 HTTP 503 capacity rejections as if they were failures. | `benchmarks/api_latency_load_test.py` caps offered concurrency to the configured limit, retries capacity rejections with backoff, reports them separately, and fails if any request does not succeed. | The harness now reports 50/50 HTTP 200 and 50/50 business-verified. |
| RR-F11 | P2 | **Wide-schema capacity was unmeasured**, so the 1 GiB cap was only justified for a 4-column schema. | `benchmarks/large_file_capacity_test.py` now parameterizes columns, string width, and CSV/Parquet input. The streaming runner caps effective chunks at `STREAM_CHUNK_CELL_BUDGET / declared columns` (default 1,000,000 cells), and the streaming metric scan reads row batches instead of projecting every column at once. | 1 GiB / 100 columns / 32-byte strings: CSV 61.65 s, 1,115.3 MiB peak; Parquet 104.71 s, 2,127.3 MiB peak (1,891.8 MiB with `MIMALLOC_PURGE_DELAY=0`). Both `LOADED`, footing matched, 0 unaccounted. `tests/test_capacity.py` and `tests/test_metric_drift_wiring.py` cover the chunk cap and batched metrics. |
